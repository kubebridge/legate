02 / Durability

How sessions recover after a crash

With SQLite or Postgres storage, session state and journaled events survive a process restart. When a session is activated again, Legate checks for interrupted work and applies its recovery policy.

A turn can resume as a new attempt or be recorded as failed. In a cluster, another node can take ownership after the previous owner's lease expires.

Ownership

Claiming a turn

Before running a turn, a worker claims it in the session store. The claim includes a lease and a token identifying the current owner. Competing claims are resolved atomically.

After Node A takes ownership, Node B's old token cannot authorise further claim-protected store writes.

The worker renews its lease while it runs. Store operations such as usage checkpoints, event appends, and settlement verify the claim token. Writes using an expired or replaced claim are rejected. Legate also checks the claim immediately before invoking a tool or notifying a completion sink.

Recovery policy

Recovering interrupted work

Set SessionOptions.OnCrashResume when opening a session. Events from the previous attempt remain in the journal whichever policy you choose.

PolicyRecovery behaviour
ResumeAttemptStart another attempt under a fresh claim, using history rebuilt from the journal. This is the session default.
FailAttemptRecord the interrupted turn as failed and return the session to idle.

When rebuilding model history, Legate removes the interrupted turn's tool-call and tool-result entries and adds a note explaining the restart.

Recovery starts a new attempt. It does not continue an interrupted HTTP request or undo an external action that already completed. Tools that change external systems need to account for retries.

Missing journal evidence is never treated as proof that an external action did not happen. When the runtime cannot tell whether an interrupted turn acted, recovery fails closed with an explicit diagnostic instead of replaying blindly or inventing what happened.

Formats

Unsupported old data versus a supported crash

Sessions carry a format marker (SessionOptions.FormatVersion, currently 1). Data from an older prerelease format is rejected before anything runs; a crash of a current-format session recovers as described above. The two cases look different and mean different things.

Unsupported old data

Opening, resuming, prompting, replying, rebinding, compacting, or forking the session fails with an unsupported-format refusal that points at a clean start. Nothing is consumed, rebound, replayed, or rewritten, and repeated attempts leave the old data untouched. Starting over is an explicit choice you make with fresh persistence: the runtime never deletes or resets local databases and never converts old records.

Supported crash recovery

Accepted inbox work survives in order, suspension and ownership identity are kept, and work that already settled is never run again. Competing owners are fenced so the loser has no effect. When the outcome is uncertain, the turn fails closed with a diagnostic rather than guessing.

Event journal

Reconnecting to the event stream

Each journaled event receives a sequence number within its session. The store assigns these numbers in order, without gaps between appended events. Pass the last sequence you processed to Subscribe to read later events, then continue with live events.

Replay after a disconnect

The sequence is an exclusive cursor: passing 42 requests events after 42. Cluster subscriptions use at-least-once delivery, so consumers should use sequence numbers to ignore events they have already processed.

Bound journal growth

Configure limits for event size, batch size, and the total event count and bytes per session. A batch that exceeds a limit is rejected before any of its events are written.

Handle retention explicitly

Journal cleanup uses its own lease to coordinate workers. If the journal has expired, replay reports that condition rather than presenting the missing history as an empty stream.

Cluster

Running across multiple nodes

Local mode runs an in-process actor system. Cluster mode distributes session actors by session ID. The session behaviour is shared between both modes.

Cluster startup

Use StaticSeeds for explicitly configured nodes or the Kubernetes package for discovery. Readiness checks determine when a node can serve traffic.

Graceful shutdown

Shutdown marks the node unready and allows running work time to finish within a configured grace period before leaving the cluster.

Message compatibility

Messages sent between nodes use versioned formats and payload-size limits. Unsupported or invalid messages are rejected. Golden-file tests check the encoded formats.

Shared model-call limits

The optional Redis coordination package applies LLM admission limits across processes, allowing multiple nodes to share the configured capacity.

Verification

Testing recovery

The repository includes a three-node Docker Compose test with Postgres and Redis. It waits until a turn enters a model call, kills the owning process with SIGKILL, then checks recovery and the event stream from a surviving node.

Additional tests cover competing claims, expired tokens, journal ordering, and stale workers being stopped before tool invocation.
